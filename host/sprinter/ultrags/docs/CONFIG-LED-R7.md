# R7: диагностика E1MAGIC Rev 1.5 через синий GPIO25 LED

Это диагностическая прошивка, не исправление R6 и не REAL PASS.
PIO-программа, частоты и способ обслуживания ISA остаются от R6.
Новая индикация добавляет нагрузку CPU/IRQ и может изменить проявление сбоя.
Сборка предназначена для показанного пользователем модуля с синим LED GPIO25,
распознаваемого прошивкой как `board=00` (PICO_BASED).

## Как запустить

1. Полностью выключить Sprinter, извлечь карту из ISA.
2. Подключить извлечённую карту по USB в BOOTSEL и записать
   `build/latest/CURRENT.UF2` обычным способом.
3. Дождаться окончания записи, отключить USB. Установить карту в выключенный
   Sprinter и включить его. USB во время проверки не подключать.
4. Выполнить в прежнем слоте:

   ```
   UGCFG GUS
   UGCFG ULTRAGS
   ```

   Для слота 1 добавлять `/SLOT:1` к обеим командам.
   Если уже первый переход GUS завершается ошибкой, не продолжать переключения:
   зафиксировать вывод и состояние LED.
5. После результата второй команды наблюдать **синий** LED не менее 20 секунд.
   Считать вспышки между длинными паузами, пропустить первую неполную группу.
   Сообщить число вспышек (или постоянное свечение/темноту) и результат UGCFG.
   При возможности снять короткое видео одновременно с выводом команды.
   Повторно SAVE, REBOOT или переключение режима не выполнять до фиксации.

Короткая вспышка — 200 мс, промежуток — 200 мс, длинная пауза — минимум
2 секунды. Группа всегда заканчивается до смены её кода. Код ошибки может
появиться с задержкой до одной группы (до 5,6 секунды).

## Коды

| Вспышки | Что установлено |
|---:|---|
| 1 | Диагностика включена после определения платы; запуск ISA ещё не дошёл до старта core1. |
| 2 | Достигнут запуск core1; core0 ещё не прошёл ожидание готовности guard и включение ISA PIO. |
| 3 | ISA PIO включён; монитор не обнаружил остановку main/guard; CONFIG-чтений пока не зарегистрировано. |
| 4 | Как 3, но ARM зарегистрировал хотя бы одно чтение CONFIG 1D0–1D2. Это не подтверждение правильного ответа или READY. |
| 5 | Защита core1 отключила ISA: IOCHRDY удерживался без завершённых операций не менее 10 мс. |
| 6 | Обновление карты портов отклонено: IOR SM не достиг допустимого PC за предусмотренное число проверок. ISA отключён. |
| 7 | Обновление карты портов отклонено из-за недопустимого base/alias. ISA отключён. |
| 8 | Не менее 500 мс не менялся счётчик основного цикла core0, при работающем диагностическом IRQ. Сам этот код ISA не отключает. |
| 9 | Main core0 работает, но не менее 500 мс нет отметок TIMER_IRQ_2 guard на core1. Сам этот код ISA не отключает. |

Стабильные 1/2 указывают этап, а не установленную причину зависания.
Коды 5–9 фиксируют **первое зарегистрированное** событие; более поздние
события его не заменяют. При одновременном обнаружении остановки main и guard
монитор выбирает main (8), что не устанавливает причинный порядок остановок.
Красный PWR и большой RGB в эту диагностику не входят.

Постоянная темнота/свечение или остановившаяся последовательность —
самостоятельный результат, а не код: возможны ранний отказ, выключенные IRQ
core0, остановка CPU, сбой тактирования, иное подключение LED или другая прошивка.
По отсутствию мигания нельзя выбрать одну из этих причин.

## Реализация и ограничения

- `UG_LED_DIAG=ON` только для ULTRAGS/HANDSHAKE; по умолчанию OFF.
- TIMER_IRQ_1/alarm1 на core0, период 25 мс, приоритет 0x80, GPIO25.
  На распознанной chipdown плате GPIO25 не захватывается: это такт M62429.
- TIMER_IRQ_2/core1 по-прежнему обслуживает guard с приоритетом 0.
  Новый heartbeat записывается и после срабатывания защиты.
- Главный цикл обновляет счётчик, чтение CONFIG — отдельный счётчик.
  Чтения чужих портов не меняют код 3 на 4.
- Первая причина и снимок GPIO, PIO CTRL/FSTAT/FDEBUG/PADOUT, PC/EXECCTRL/
  SHIFTCTRL обоих SM, стадия и счётчики сохраняются в
  `ug_led_first_fault` в SRAM **до отключения ISA**. RX FIFO не читается;
  FDEBUG не очищается. Снимок не атомарен относительно работающего PIO.
- Запись причины публикуется после снимка через acquire/release CAS.
  Копирование не использует printf, USB, Flash или ISA-команды.
- Запись теряется после сброса/выключения; это не журнал во Flash.
- LED работает из IRQ core0: не гарантирует индикацию при остановке обоих
  ядер, отключённых IRQ core0 или отказе таймера/тактового генератора.
- Это проверка запуска/CONFIG. Для приёмки аудио и производительности
  диагностическую IRQ-нагрузку потребуется убрать.

## Проверки

Фактические результаты и SHA256 сохраняются в `build/latest/LED.json`
и `build/latest/led-evidence/`. HOST проверяет production C индикации:
коды 1–9, полные группы, переход состояния, переполнение 32-битного времени,
остановку main/guard, сохранение первой причины и пассивный снимок регистров.
Отдельно проверяются production C handshake с включёнными/выключенными
диагностическими hooks, CONFIG exchange, MULTIFW каталог/UF2 и идентичность
двух независимых сборок. Это не воспроизведение отказа физической карты.

S6/S7 остаются IN_PROGRESS. R6 имеет REAL FAIL.

## REAL: ответ владельца 2026-10-20

После `UGCFG ULTRAGS`: `TIMEOUT / RESULT FAIL`, синий LED повторяет
четыре вспышки каждые 3–4 секунды. Это соответствует коду 4
(полный цикл 3,6 секунды). Запуск через UGCFG по-прежнему REAL FAIL.
Диагностика зарегистрировала CONFIG-чтения и не обнаружила остановки
main/guard либо событий отключения ISA 5–7. Это не доказывает правильность
CONFIG-ответов, готовность аудио или причину отказа прежних сборок.

Следующий шаг в этом состоянии: `TRC0` для прежнего слота 0/base02A0
(для известного слота 1 — `TRC1`). Зафиксировать весь вывод и код LED.
До этого не выполнять SAVE, REBOOT, INFO или переключение режима:
INFO изменит сохранённые CONFIG trace-поля. TRC читает native STATUS/ERROR
и диагностические регистры, не меняя CONFIG-селектор.
Опубликованная R7 выдача и её hashes остаются неизменными.

Фото `photo_2026-10-20_15-28-26.jpg`: после TIMEOUT все 16 строк TRC0
показывают `STATUS=FF ERROR=FF SEL=FF RAW=FF COUNT=FF FLAGS=FF`.
Это не достоверные значения внутренних trace-полей: native-ответы также
не получены. Затем владелец сообщил, что после длительной паузы LED
стал выдавать код 5. Он означает первое зарегистрированное срабатывание
guard: запрос WAIT в PIO оставался активным без изменения счётчика
завершений не менее 10 мс; прошивка отключила обе ISA SM и драйверы.
Это наблюдение внутреннего состояния PIO, не измерение электрического
IOCHRDY на разъёме ISA. После отключения дальнейшие FF ожидаемы.
По уточнению владельца, код 5 замечен через примерно 1–2 минуты, после
фотографирования экрана и переноса фото на Mac, перед выключением.
Сам переход 4→5 не наблюдался; время срабатывания относительно TRC0
неизвестно. Это время обнаружения, а не измеренная задержка guard.
Новые команды не упомянуты; отсутствие транзакций ISA не измерялось.
Нельзя приписывать первоначальные TIMEOUT/FF этому срабатыванию без
данных о последовательности событий.
