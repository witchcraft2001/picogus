## Что измеряет R11

Для чтения DATA_HIGH прошивка снимает GPIO непосредственно перед записью
подготовленного байта в TX FIFO. В linked ARM-коде это соседние LDR/STR:
`SIO GPIO_IN (D0000004)` → `PIO0 TXF1 (50200014)`.
Только после отправки обновляются диагностические поля.
Если `/IOR` был высоким, ответ не мог завершить этот цикл: байт ещё не был
отправлен. Сохраняются число таких случаев, индекс и отправленный байт,
а также уровень обратного входа WAIT. Учитываются только впервые потреблённые
байты каталога 0…147. Чтения после конца потока не создают ложных событий.

**Предел покрытия:** FLAGS=A4 подтверждает только наличие хотя бы одного
учтённого байта. Внутренний `seen` утилита не выводит. Проба не учитывает
чтения, отброшенные ранней stale-проверкой до DATA_HIGH, и не подтверждает
обработку всех 148 запросов. Поэтому LATE=0 не исключает потерянный запрос
до точки измерения. INDEX=FF/SENT=FF при LATE=0 — пустые поля; из них нельзя
заключить, что ARM отправил FF для повреждённого байта.

**Нулевой счётчик не доказывает успешный приём.** Не измеряются момент выборки
данных хостом, принятие WAIT, задержка трансиверов и доставка байта после
FIFO. Проба добавляет GPIO-чтение и меняет расположение/расписание ARM-кода:
положительный результат доказывает позднюю отправку в R11, но сам по себе
не доказывает тот же механизм в R10.

**LATE=0 при FAIL не означает «WAIT не принят».** IOR может ещё оставаться
низким после выборки данных хостом; также возможна задержка после отправки
в FIFO. По этому результату нельзя однозначно выбрать аппаратную правку
или ускорение ARM. LATE>0 тоже не исключает слишком позднее утверждение WAIT.
Сравнение времени обычных чтений 1D0 и пустого адреса не является достаточной
проверкой WAIT: нужен контролируемый длинный hold, который должен добавить TW,
и подтверждённая точность измерения.

PIO IOW10/IOR22 побайтно совпадает с R10. LED/USB-диагностика отключена.
Шесть других образов побайтно совпадают с R10. API VLS1 не меняется:
временные read-only поля 1C…1F доступны только с `UG_CONFIG_PROBE=ON`.
Опция по умолчанию OFF и требует COMPAT/HANDSHAKE без CONFIG_TRACE.

## Команды на карте

Первый замер уже выполнен (20:38). Перепрошивка и повторение переключений
ради того же замера не требуются. Для анализа сдвига/замен в потоке полезен
один полный `UGCFG INFO /DIAG` на текущем состоянии. Он начнёт новое чтение
и сбросит пробу; результат предыдущей пробы уже сохранён на фотографии.
Измерение /IOR и IOCHRDY требует отдельного согласования доступного прибора.

Ниже исходная процедура установки R11 для воспроизводимости.

Прошить **CURRENT.UF2 при выключенном Sprinter**; отключить USB до включения.
Скопировать EXE из CURRENT.ZIP/IMG. Для слота 0, native BASE02A0:

```text
UGCFG GUS
UGCFG ULTRAGS
UGCL0
```

**После ULTRAGS, даже если она дала FAIL, сразу выполнить UGCL0.**
Между ними не выполнять INFO, смену режима или SAVE: новый выбор каталога
сбрасывает измерение. Сфотографировать оба вывода. UGCL0 ничего не пишет
в порты карты и не читает потребляющие DATA/RESPONSE; диагностический
выход не является RESULT PASS.

Если ULTRAGS и UGCL0 отработали без ошибки, выполнить один дополнительный замер:

```text
UGCFG INFO /DIAG
UGCL0
```

Снова сохранить оба вывода. Для слота 1 к командам UGCFG добавить `/SLOT:1`
и использовать **UGCL1**. При `WRONG FIRMWARE / BASE / SLOT` сохранить экран
и остановиться. TRC0, UGW0, SAVE и ожидание кодов LED не нужны.

## Расшифровка

Все числа в строке UGCL — HEX; INDEX отсчитывается от нуля.

| Поле | Значение |
|---|---|
| LATE | Число байтов, перед отправкой которых `/IOR` уже был высоким |
| INDEX | Индекс последнего такого байта; FF при отсутствии события |
| SENT | Значение, подготовленное ARM для последнего события |
| FLAGS=A0 | Новый каталог ещё не читался |
| FLAGS=A4 | Есть отсчёты, высокого `/IOR` перед отправкой не зарегистрировано |
| FLAGS=A5 / A7 | Есть поздний ответ; обратный вход WAIT в момент отсчёта low / high |
| STATUS / ERROR | Текущие native-регистры карты |

Например, `LATE=01 INDEX=65 SENT=C8 FLAGS=A7` означает один поздний ответ
для байта 101 со значением C8. Это пример, а не ожидаемый обязательный результат.
Поле WAIT сообщает уровень GPIO26, а не подтверждение принятия WAIT хостом.

## Проверки и доказательства

* Две независимые MULTIFW-сборки дают одинаковый UF2.
* Linked-проверка исполняет участок Thumb между метками пробы для всех
  256 значений: GPIO-чтение непосредственно перед единственной FIFO-записью,
  без вызовов функций и записи счётчиков до неё.
* Production C/UBSan: инъекция завершённого IOR на байте 101, чтение четырёх
  native-полей, конец потока и сброс новой сессии; 213 CONFIG-операций.
* 112 запусков реальных UGCL EXE в Z80-модели: оба слота, IFF, Turbo,
  нормальные/ошибочные поля; только шесть разрешённых чтений, ни одной
  записи в карту. Две сборки UGCL совпадают.
* Регрессии PIO: 262144 адресных комбинации, 1280 CONFIG/GS байтов,
  12288 независимых случаев rp2040js, включая 384 отмены native-чтения;
  production core1 guard + UBSan.
* 270 сценариев UGCFG; девять основных EXE пересобраны и совпадают с R10.
  SRAM/Settings и статический stack budget проверены.
* Обратное чтение ZIP/FAT12 IMG, hashes и исходники — `R11.json`, `evidence/`.

Эти проверки подтверждают реализацию измерения и локальные регрессии.
Аппаратное восстановление и приёмка этапа остаются открытыми.
