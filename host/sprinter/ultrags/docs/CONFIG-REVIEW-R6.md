# R6: аппаратный rearm чтения IOR

## Аппаратный результат: REAL FAIL

Фото `photo_2026-10-20_13-16-43.jpg`: переключение в ULTRAGS снова
завершается TIMEOUT; все 16 строк TRC0 содержат FF во всех полях.
Пользователь дополнительно подтвердил: светодиод PicoGUS после TIMEOUT погас.
В этой сборке LED переключается после включения ISA PIO и ожидания готовности
guard, перед processSettings(). Это свидетельствует о прохождении данного
участка запуска; работоспособность последующего обмена и состояние guard
по светодиоду не определяются.

R6 отклонена. Следующие HOST PASS описывают только программные проверки
и не являются подтверждением исправления аппаратного отказа.
Причина REAL отказа пока не установлена.

Уточнение аппаратуры по фото пользователя `photo_2026-10-08_14-50-07.jpg`:
стенд использует E1MAGIC PicoGUS REV 1.5 с отдельным USB-C модулем,
внешне похожим на YD-RP2040, а не штатную chipdown PicoGUS 2.0.
Схема именно этой ревизии и соответствие наблюдаемого LED управляемому
прошивкой GPIO пока не подтверждены. Поэтому погасший LED нельзя считать
доказательством прохождения участка запуска, указанного выше.
Развязка питания штатной PicoGUS 2.0 не доказывает безопасность одновременного
подключения ISA и USB на этом клоне; прямое подключение к Mac отложено
до подтверждения схемы или изготовителя.

Пользователь уточнил индикаторы: синий возле USB погас, красный продолжил
гореть; большой RGB при работе PicoGUS не светится. В опубликованной схеме
YD-RP2040 2022-V1.1 синий LED подключён к GPIO25, красный PWR — к 3V3,
RGB — WS2812B на GPIO23. Историческое INFO `board=00` означает PICO_BASED
(`common/picogus.h`), для которого прошивка использует GPIO25 как LED.
Однако main также включает и выключает GPIO25 до выбора BOARD_TYPE,
во время ADC определения платы. Поэтому одно конечное состояние «синий
погас» не различает ранний участок и переключение LED после запуска ISA PIO.
Красный PWR свидетельствует о наличии питания, но не измеряет его качество
и не доказывает работу CPU. RGB не является индикатором этого пути прошивки.

Дополнительное исследование: фактическая 32-словная программа R4/R5/R6
в независимой модели rp2040js проходит отдельный native read и освобождение
шины. Exploratory запуск linked ARM main вместе с PIO-моделью также проходит
CONFIG selector/protocol и native STATUS/ERROR при заданных длинных циклах.
Короткие модельные циклы теряют часть CONFIG обменов, но устойчивый all-FF
аппаратного стенда не воспроизведён. Эти эксперименты не моделируют
электрические задержки платы, IRQ guard на core1 и реальный тайминг Sprinter;
они не входят в опубликованный комплект acceptance evidence.

## Основание

REAL 2026-10-20 12:42:22: R5 после UGCFG ULTRAGS TIMEOUT возвращает FF
во всех16 строках TRC0, включая native STATUS/ERROR. Это регрессия относительно
R4. Срабатывание fuse, остановка PIO и незапуск по этому снимку не различаются.
R5 отклонена. Причина аппаратного отказа пока не установлена.

## Изменения

При пассивном завершении ARM проверяет высокий IOR через SIO и принудительно
переходит к restart. R5 сразу ждала низкий IOR. Наблюдение high через SIO не
гарантирует high на входе данного SM: повторный захват прежнего цикла возможен.

- Restart теперь выполняет WAIT1→WAIT0 в PIO. На чужом цикле не меняет ADS,
  WAIT и направления данных. Высокий уровень подтверждается самим SM.
- Map publication разрешена и на WAIT1, и на WAIT0, а также в parked;
  production-C проверка покрывает оба idle положения.
- Matching branches держат WAIT четыре clocks перед первым snapshot вместо
  трёх. Это запас для output-to-input ownership feedback; электрический запас
  на RP2040/Sprinter не измерен.
- IOW SET ADS + SET X1 + два JMP X-- занимают прежние16 setup clocks.
  Освободившееся слово отдано WAIT1. Программа остаётся32 words.

Номера API/CONFIG/Settings не менялись. Основные UG EXE прежние. Диагностический
trace overlay включён, но частью API1.0 не является.

## Проверки и пределы

- Generated PIO:512 maps /1048576 addresses /524288 writes;288 INFO/CRC streams,
  DACK, полный RX FIFO,12 coupled phases,256 mux patterns — PASS.
- Новый тест4096 случаев: при возврате ARM на restart с ещё низким IOR в SM
  R5 повторно захватывает старый цикл; R6 ждёт high→low и захватывает новый один раз.
- Четыре ownership случая с заданной задержкой feedback3 ticks: R5 теряет
  первый tag, R6 сохраняет. Frozen R5 source имеет SHA256
  b3cbf8ac82e181d8322f149461f593c33ff94b210936308b05efeeb3208944cc,
  совпадающий с исходником предыдущей поставки.
- Это модели с заданным skew, не измеренные задержки стенда и не доказательство
  того, что именно они вызвали все FF на последнем фото.
- Production C exchange/guard/init, linked ARM CONFIG read/deadline, regression
  write-window,10 linked audio profiles, stack, SRAM/Settings, SAVE clock,
  PSRAM ID — проверяются на свежем ELF; результаты хранятся в trace-evidence.
- Другие шесть mode images совпадают с baseline кроме SDK date.
- Путь запуска R5 в exploratory Unicorn fixture дошёл до multicore_launch_core1
  без assertion; HAL там моделируется. Это не полноценный boot/hardware gate.

Полный повтор всех HOST/DSS тестов приложений не заявляется. REAL R6_PENDING;
приёмка S6/S7 остаётся IN_PROGRESS. Ожидается восстановление native и CONFIG,
но программные PASS этого не доказывают.

## Команды на стенде

Постоянная точка выдачи: `build/latest/CURRENT.ZIP`, файл `CURRENT.UF2`.
После прошивки через USB BOOTSEL, в том же slot0/base02A0:

```text
UGCFG ULTRAGS
TRC0
```

Снять оба результата, даже при PASS. Между ними не выполнять другие UG-команды.
Если переключение PASS:

```text
UGCFG INFO /DIAG
UGCFG VERIFY
UGMEM INFO
```

Slot1: `/SLOT:1` у UG-команд и `TRC1`. При TIMEOUT остановиться после TRC;
SAVE/GSALIAS и аудиотесты пока не нужны. Исторический PGMULTI.UF2 — R3,
текущий кандидат определяется CURRENT.UF2 и хешами TRACE.json.
